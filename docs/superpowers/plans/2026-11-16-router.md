# Router dell'ambito (lezione 6, step 1) — piano di implementazione

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** un nodo LLM prima dell'agente classifica la domanda (`conversazione` / `fuori_ambito`) secondo un ambito descritto in `config/ambito.txt`; fuori ambito → rifiuto fisso con il motivo, senza eseguire l'agente.

**Architecture:** `config/ambito.txt` (descrizione + esempi) letto all'avvio (`SCOPE_FILE`). Nuovo modulo `assistant/router.py`: schema `Route`, prompt del router, scelta dei messaggi di contesto, costruzione della funzione di classificazione (stesso modello, `reasoning_effort="none"`, `json_schema`), testo del rifiuto. `build_graph` riceve un `router` facoltativo: con router, `START → router → model | refusal`. `stream_view` stampa il rifiuto. `__main__` collega tutto.

**Tech Stack:** Python 3.14, LangGraph 1.2.17, langchain-core 1.7.0, langchain-openai 1.7.2, pydantic (già installato con LangChain); nessuna nuova dipendenza.

**Spec:** `docs/superpowers/specs/2026-11-16-router-design.md`

**Verificato prima del piano (2026-11-16):** `ChatOpenAI` mette `reasoning_effort` nel payload sia con `model_copy(update={"reasoning_effort": "none"})` sia nel costruttore; LM Studio con `reasoning_effort: "none"` non manda ragionamento; `json_schema` con i campi `categoria`/`motivo` dà JSON valido; prompt della sonda con esempi = 9/9 (testo base del file qui sotto).

  - log: `[router] categoria=<categoria> motivo=<motivo> → agente` oppure `→ rifiuto` (INFO, logger `assistant.graph`); `[router] risposta non valida (<errore>): la domanda passa all'agente` (WARNING).
  - errore di configurazione: `SCOPE_FILE non valida: '<percorso>' non esiste o è vuoto.`

## Review Focus

1. **Domanda fuori ambito**: il modello dell'agente non deve essere chiamato affatto (il modello finto non consuma messaggi). Test nel Task 3.
2. **Router che restituisce JSON non valido** (eccezione di parsing o di validazione): la domanda passa all'agente; un errore di collegamento (`openai.APIError`) invece si propaga come oggi. Test nel Task 3.
3. **Domanda di seguito** («e a Tokyo?»): il contesto del router contiene la domanda precedente in testo, senza `ToolMessage` né messaggi con chiamate. Test nel Task 2.
4. **Streaming**: i pezzi del router non compaiono; il rifiuto compare una volta. Test nel Task 3.
5. **File dell'ambito mancante o vuoto**: errore chiaro all'avvio, codice 1, nessun traceback. Test nei Task 1 e 4.

### Task 3: Router nel grafo, rifiuto e streaming

**Files:**
- Modify: `assistant/graph.py`, `assistant/stream_view.py`
- Test: `tests/test_graph.py`, `tests/test_stream_view.py`

**Interfaces:**
- Consumes: `Route`, `refusal_text` (Task 2).
- Produces: `build_graph(model, tools, max_steps, answer_check=None, router: Callable[[list[AnyMessage]], Route] | None = None)`. `State` acquista il campo facoltativo `route: str` (`NotRequired`) con la categoria del turno. Nodi nuovi, solo se `router` è dato: `router` e `refusal`.

**Comportamento (deciso qui):**
- Con router: `START → router`; arco condizionale dopo `router`: `"model"` se la categoria è `conversazione`, `"refusal"` se `fuori_ambito`; `refusal → END`. Senza router: `START → model` come oggi.
- Nodo `router`: chiama `router(state["messages"])`; `OutputParserException` (da `langchain_core.exceptions`) o `ValueError` (comprende `pydantic.ValidationError`) → `WARNING` e categoria `conversazione`; ogni altra eccezione si propaga. Log `INFO` come nei Global Constraints. Restituisce `{"route": categoria}` più, per il rifiuto, il motivo (campo `NotRequired` `route_reason: str`, o equivalente nello stato: scelta dell'implementer, motivata nel report). Non aggiunge messaggi e non cambia `steps`.
- Nodo `refusal`: `{"messages": [AIMessage(refusal_text(...))]}`.
- `stream_turn`: nell'aggiornamento del nodo `refusal` → `view.extra(contenuto del messaggio)`. I pezzi dei nodi diversi da `model` sono già ignorati: un test lo conferma per `router`.

- [ ] **Step 1: Write the failing tests**
  - `tests/test_graph.py` (con `fake(...)` e un router finto `lambda msgs: Route(...)` che registra le chiamate):
    - `test_router_in_scope_runs_agent`: `conversazione` → risposta del modello finto, router chiamato una volta, log `[router] categoria=conversazione motivo=… → agente`.
    - `test_router_out_of_scope_refuses_without_agent`: `fuori_ambito` con motivo `cucina` → ultimo messaggio `== REFUSAL.format(motivo="cucina")`; il modello finto non è stato chiamato (il suo iteratore ha ancora il messaggio: per esempio `next(model.messages)` funziona dopo); `steps == 0`; log con `→ rifiuto`; nessun log del nodo `model` (con `caplog` a DEBUG, nessuna riga `[grafo] nodo model`).
    - `test_router_invalid_output_falls_back_to_agent`: router che solleva `OutputParserException("x")` → risposta del modello, log `WARNING` `[router] risposta non valida`.
    - `test_router_api_error_propagates`: router che solleva un `openai.APIConnectionError` → l'eccezione esce dal grafo.
    - `test_router_does_not_add_messages`: con `conversazione`, i messaggi finali sono quelli di oggi (System, Human, AI).
    - i test esistenti senza router restano invariati.
